# schema v2.md｜繼電器 LLM Wiki 規則檔

> 本檔是維護這個 Wiki 的最高規則。AI 每次執行 ingest、query、lint 或生成簡報前，都要先讀這份檔案。
> 本檔與其他頁面衝突時，以本檔為準。修改本檔需要使用者同意，並寫入 `log.md`。

---

## 0. 專案概要

| 項目 | 內容 |
|---|---|
| 主題 | 繼電器（Relay） |
| 讀者 | 想做 Arduino／ESP32 專題的自造者：會一點程式，但不懂硬體 |
| 最終產出 | 教學 HTML 簡報（25 張以內，含圖、出處、takeaway、小測驗） |
| 架構 | Karpathy LLM Wiki：原始資料（raw）→ Wiki 頁面（wiki）→ 產出（output） |

### 0.1 學習目標（範圍內）

- **G1 懂原理**：知道繼電器怎麼用小電流控制大電流，也分得清 COM／NO／NC
- **G2 會接線實作**：能用 ESP32 接繼電器模組，並知道要接返馳二極體
- **G3 懂安全**：分得出低壓和 110V 市電的風險，知道什麼情況不該自己接

### 0.2 範圍外

- 選型細節，例如觸點額定計算、壽命曲線、型號比較
- 替代方案，例如 SSR、MOSFET、接觸器的深入比較

範圍外的內容最多寫一句話帶過，並標上 `（範圍外，不展開）`。要不要收錄，依第 9 節的停止條件處理。

## 2. 命名規則

- 檔名一律使用**英文小寫 kebab-case**，並加上類型前綴，例如 `concept-flyback-diode.md`、`howto-esp32-12v-pump.md`
- 來源編號為 `src-01`、`src-02`……依吸收順序遞增，永不重複使用；來源頁的檔名為 `source-01-<slug>.md`
- 頁面內的連結用 `[[檔名不含副檔名]]`，例如 `[[concept-no-nc-com]]`
- 頁面標題（H1）使用繁體中文

---

## 3. 語言與寫作規則

1. 內文一律使用**繁體中文**（台灣用語）
2. 術語**在每一頁第一次出現時**以括號附上英文，例如「常開（NO, Normally Open）」；同一頁後面再出現時，不必重複附英文
3. 每個術語都必須收進 `glossary.md`
4. 以 Arduino／ESP32 自造者的程度書寫：
   - 可以假設讀者知道 GPIO、`digitalWrite()`、麵包板
   - 不可以假設讀者知道電感、反電動勢、電晶體飽和；用到時要用一句白話解釋，或連到概念頁
5. 每段不超過 5 句；一句只講一件事
6. 數值必須寫出單位，例如 `5 V`、`10 A`、`250 VAC`
7. 不可以寫出沒有出處的事實、數字或安全建議（見第 5 節）

## 4. 頁面類型與模板

所有頁面（名詞表、矛盾清單、日誌除外）都要以 YAML frontmatter 開頭：

```yaml
---
id: concept-flyback-diode
type: concept            # concept | component | howto | safety | source | index
title: 返馳二極體
goals: [G1, G2]          # 對應的學習目標
sources: [src-02, src-05]
status: draft            # draft | reviewed | needs-check
updated: 2026-11-23
---
```

### 4.1 概念頁 `concept-*`

一頁講一個觀念，例如電磁鐵原理、COM／NO／NC、線圈與觸點、返馳二極體。

```markdown
# <概念名稱>

## 一句話說明
<30 字以內，新手一看就懂> [src-xx]

## 為什麼要知道這個
<跟自造者實作的關係>

## 原理
<分段說明，每個事實句都要標出處>

## 常見誤解
- <誤解> → <正確說法> [src-xx]

## 相關頁面
- [[...]]

## 簡報素材
- **Takeaway**：<一句話結論>
- **圖說描述**：<描述一張圖要畫什麼，讓人可以照著畫成 SVG，例如元件、標示、箭頭方向>
- **測驗題**：
  - 題目：...
  - 選項：A. ... B. ... C. ... D. ...
  - 答案：...｜解析：... [src-xx]
```

### 4.2 元件頁 `component-*`

一頁講一種實物，例如 5V 單路繼電器模組、光耦隔離模組。

```markdown
# <元件名稱>

## 長什麼樣子
<外觀與腳位描述>

## 腳位／端子說明
| 腳位 | 功能 | 接到哪裡 | 出處 |
|---|---|---|---|

## 關鍵規格（只列實作會用到的）
| 項目 | 常見值 | 出處 |
|---|---|---|

## 觸發方式
<高電位或低電位觸發；如有矛盾，依第 6 節處理>

## 注意事項
- ... [src-xx]（牽涉安全時要連到 [[safety-*]]）

## 相關頁面
## 簡報素材
<同 4.1>
```

### 4.3 實作頁 `howto-*`

一步一步的接線流程，例如「ESP32 控制 12V 泵浦」。

```markdown
# <實作名稱>

> ⚠️ 安全等級：低壓 DC／市電（市電頁面必須連到 [[safety-mains]]）

## 目標
## 材料表
| 品項 | 數量 | 規格 | 備註 |
|---|---|---|---|

## 接線圖說明
<逐條列出：A 腳 → B 腳>

## 步驟
1. ... [src-xx]
2. ...

## 範例程式
（Arduino／ESP32 程式碼，附註解）

## 常見問題排除
| 症狀 | 可能原因 | 解法 | 出處 |
|---|---|---|---|

## 相關頁面
## 簡報素材
<同 4.1>
```

### 4.4 安全頁 `safety-*`

注意事項和禁止事項，例如市電風險、電流超載。

```markdown
# <安全主題>

## 🚫 絕對不要
- ... [src-xx]

## ⚠️ 必須注意
- ... [src-xx]

## ✅ 安全的做法
- ... [src-xx]

## 什麼時候該找專業人士
## 相關頁面
## 簡報素材
<同 4.1>
```

安全頁的規則：

- 每一條都必須有出處，而且至少一個出處的可信度要在 B 級以上（見 5.2）
- 用語要保守、明確，避免使用「通常沒事」「應該可以」這類說法

### 4.5 來源頁 `source-*`

每份網路資料一頁。

```markdown
---
id: source-03-xxx
type: source
src: src-03
title: <原文標題>
url: <網址>
author: <作者或機構，未知時寫「不明」>
published: <發布日期，未知時寫「不明」>
retrieved: 2026-11-23
credibility: B      # A | B | C | D
language: zh-TW
raw: raw/src-03_xxx.md
---

# <原文標題>

## 重點摘要
- <用自己的話寫 3～7 點；不可大段照抄>

## 可信度說明
<為什麼給這個等級>

## 被引用的頁面
- [[...]]

## 備註
<過時、偏頗、範圍外等提醒>
```

### 4.6 名詞表 `glossary.md`

依中文筆畫或注音排序，每個詞條格式如下：

```markdown
### 常開接點（NO, Normally Open）
線圈沒通電時斷開，通電後才接通的接點。[src-xx]
→ 詳見 [[concept-no-nc-com]]
```

### 4.7 索引頁 `index.md`

- 依頁面類型分區，列出每一頁的標題、一句話說明和狀態（draft／reviewed／needs-check）
- 另設一區「依學習目標」，列出 G1、G2、G3 各自涵蓋哪些頁面
- 最下方記錄統計：總頁數、來源數、未解決的矛盾數

### 4.8 日誌 `log.md`

只能新增，不能修改舊紀錄，最新的寫在最上面：

```markdown
## [2026-11-23] ingest | src-03 <標題>
- 新增：[[...]]
- 修改：[[...]]（改了什麼）
- 新增矛盾：C-02
- 使用者確認：✅
```

動作類型：`ingest`、`query`、`lint`、`slides`、`schema`（修改規則檔）、`resolve`（解決矛盾）。

## 5. 出處規則

### 5.1 標註層級：句子層級

- 每個**事實句、數字、規格、安全建議**後面都要標 `[src-xx]`
- 多個來源寫成 `[src-02][src-05]`
- 只用來串接的句子（例如「接下來看接線」）不必標
- AI 自己的推論、整理或比喻要標 `[整理]`，而且不可以用於數字和安全建議
- 數值後面要盡量附上原文所在位置，例如 `[src-02 §3]` 或 `[src-02 表 1]`

### 5.2 可信度等級

| 等級 | 來源類型 |
|---|---|
| A | 原廠 datasheet、原廠應用筆記 |
| B | 教科書、大學講義、標準文件 |
| C | 知名教學網站，例如 SparkFun、Adafruit、Random Nerd Tutorials |
| D | 論壇、個人部落格、影片留言、問答網站 |

- 安全相關內容至少要有一個 B 級以上的來源
- 只有 D 級來源支持的事實，要在內文加上 `（僅有論壇來源）`

## 6. 矛盾處理

**原則：AI 不自行裁決，一律記錄在矛盾清單，由使用者判斷。**

1. 發現兩個來源說法不同時，在 `contradictions.md` 新增一筆紀錄：

```markdown
## C-01｜繼電器模組 IN 腳的觸發電位
- 狀態：🟡 待查         # 🟡 待查 | 🟢 已解決
- 說法 A：低電位觸發 [src-02]（可信度 C）
- 說法 B：高電位觸發 [src-04]（可信度 D）
- 影響頁面：[[component-5v-relay-module]]
- 是否與安全有關：否
- AI 觀察：<可能的原因，例如模組版本不同；只供參考，不是結論>
- 使用者裁決：（空白，等使用者填寫）
```

2. 正文中受影響的段落改寫成：

```markdown
> ⚠️ 待查（C-01）：來源對此說法不一，見 [[contradictions]]。
```

   同時把該頁的 `status` 改成 `needs-check`。

3. 使用者裁決後，依裁決改寫正文，把狀態改成 🟢，並在日誌記一筆 `resolve`。
4. 與安全有關的矛盾在解決之前，相關內容不可以放進簡報。

## 7. 工作流程

### 7.1 Ingest（吸收資料）：一次一篇

1. 把原文存成 `raw/src-xx_<slug>.md`（之後唯讀）
2. 建立來源頁 `source-xx-*.md`，並評定可信度
3. 列出這篇資料會影響哪些頁面（新增或修改）
4. 檢查有沒有觸發第 9 節的停止條件；有的話先停下來問使用者
5. 更新相關頁面、名詞表和矛盾清單
6. 向使用者回報：
   - 這篇資料的 3～5 點重點
   - 新增和修改了哪些頁面（修改的要說明改了什麼）
   - 新增的矛盾和術語
7. **等使用者確認**後，更新 `index.md`、寫入 `log.md`，才能處理下一篇
8. 使用者要求修改時，改完再回報一次

### 7.2 Query（提問）

- 只能根據 Wiki 內容回答，並標出引用的頁面和來源
- Wiki 沒有的內容要明說「Wiki 中沒有這項資料」，不可以用 AI 自己的知識補上
- 回答中有值得保存的整理，可以建議使用者新增成頁面，但要使用者同意才寫入

### 7.3 Lint（健檢）：只列報告，不自動修正

報告分成三個等級：

- 🔴 **錯誤**：必須修正，否則不能生成簡報
- 🟡 **警告**：建議修正
- 🔵 **提示**：可改可不改

| # | 檢查項目 | 規則 | 等級 |
|---|---|---|---|
| L1 | 出處 | 事實句、數字句都有 `[src-xx]`，而且對應的來源頁存在 | 🔴 |
| L2 | 連結 | 沒有斷掉的 `[[連結]]`；沒有沒被任何頁面連到的孤兒頁 | 斷連結 🔴／孤兒頁 🟡 |
| L3 | 術語 | 術語第一次出現時附英文，而且都收進名詞表 | 🟡 |
| L4 | 矛盾 | 待查的矛盾沒有被寫成定論；正文標記和清單一致 | 🔴 |
| L5 | 安全 | 牽涉市電或大電流的頁面都連到安全頁並附警告；安全內容有 B 級以上來源 | 🔴 |
| L6 | 格式 | frontmatter 完整；各頁面類型的必要區塊都有 | 🟡 |
| L7 | 新手可讀性 | 沒有未解釋的術語、超過 5 句的段落、超出讀者程度的內容 | 🟡 |
| L8 | 簡報素材 | 概念頁、元件頁、實作頁、安全頁都有 takeaway、圖說描述和至少 1 題測驗題 | 🟡 |

報告格式：

```markdown
# Lint 報告 2026-11-23
摘要：🔴 2｜🟡 5｜🔵 1

## 🔴 錯誤
- [L1] concept-flyback-diode 第 3 段：「1N4007 最常用」沒有出處
- ...

## 建議修正順序
1. ...
```

Lint 結果的摘要要寫入 `log.md`。

### 7.4 生成簡報

前提：通過第 10 節的完成條件，而且使用者下了指令。

| 項目 | 規則 |
|---|---|
| 張數 | 25 張以內 |
| 建議結構 | 封面 → 學習目標 → G1 原理 → G2 接線實作 → G3 安全 → Takeaway 總結 → 小測驗 → 參考資料 |
| 圖 | 依各頁的「圖說描述」畫成 SVG；每張圖都要有圖說 |
| 出處 | 每張投影片底部以小字標 `[src-xx]`；最後一頁列出完整參考資料（標題、作者、網址、擷取日期） |
| Takeaway | 每個章節結尾 1 張，或者全部放在最後 1 張統整 |
| 小測驗 | 5～8 題，從各頁的測驗題素材挑選，附答案和解析 |
| 安全 | 介紹市電內容的投影片要有醒目的警告標示 |
| 檔案 | 存成 `output/slides/relay-intro-<日期>.html`，為單一自含式 HTML |

簡報內容只能來自 Wiki，不可以加入 Wiki 沒有的事實。

## 8. 觸發條件

| 動作 | 什麼時候執行 |
|---|---|
| ingest | 使用者提供一篇資料並說「吸收」時才執行；AI 不主動上網找資料 |
| lint | ① 每累積吸收 5 篇自動執行一次 ② 使用者說「lint」時 ③ 生成簡報前一定要先跑一次 |
| 生成簡報 | 使用者下指令，而且通過第 10 節的完成條件 |
| query | 使用者提問時 |
| 修改 schema | 只有使用者明確要求時 |

---

## 9. 停止條件（必須停下來問使用者）

遇到以下任一情況，AI 要暫停、說明情況，等使用者決定：

1. **矛盾**：發現來源之間的說法互相矛盾
2. **安全內容來源不足**：牽涉市電或大電流，但只有 C、D 級來源
3. **改動過大**：一篇資料會修改 5 頁以上
4. **破壞性改動**：要刪除頁面，或大幅改寫既有內容（一段以上）
5. **資料品質低**：來源不明、沒有作者或日期，或只有 D 級來源，先問要不要收錄
6. **超出範圍**：內容屬於第 0.2 節的範圍外項目，先問要不要收錄
7. **規則不適用**：碰到本檔沒有規定的情況

---

## 10. 完成條件（可以生成簡報的門檻）

以下全部達成，才能生成簡報：

- [ ] G1、G2、G3 每個學習目標都至少有 1 頁概念頁或實作頁
- [ ] 每個學習目標都有 **2 個以上的獨立來源**
- [ ] `contradictions.md` 中沒有還沒解決、而且與安全有關的矛盾
- [ ] 最近一次 lint 沒有 🔴 錯誤
- [ ] 至少有 1 頁實作頁的 `status` 是 `reviewed`

AI 被要求生成簡報時，要先逐項回報這份清單的狀態；有未達成的項目就停下來，說明還缺什麼。
